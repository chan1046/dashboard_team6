# Model 2 고장 30분 전 부분 센서 이력 가용성 감사

모델을 학습하지 않았고, 기존 Model 1·Model 2·RUL 모델과 Train/Validation 분할을 변경하지 않았다. 예약·제외 사건은 사용하지 않았다. `full_fault_type_baseline/eligibility.csv`의 **동일 사건, 동일 고장−30분 예측 시점, 직전 30분 실제 센서 창**을 재검증했다. 정지 구간의 센서값을 보간·forward fill하거나 가짜 관측을 만들지 않았다. [사건별 실제 이력과 품질](history_quality.csv), [실험 설정](config.json).

## 기대 관측량과 이전 strict 기준

Tool별 대표 간격은 **Train에서만** 계산했다. 두 인접 실제 센서 행이 모두 `FIXTURESHUTTERPOSITION=1`이고, Train의 앞뒤 모든 유형 고장에서 24시간 넘게 떨어져 있으며, 다음 24시간의 고장 여부를 Train 안에서 확인할 수 있는 구간만 사용했다. Validation의 측정 간격이나 고장 정보를 기준 계산에 사용하지 않았다. 20대 모두 인접 관측 간격 중앙값이 **4초**였으므로 `30분 / 4초 = 약 450행`을 기대 관측량으로 삼았다. 각 창의 `observation ratio = 실제 센서 행 수 / 450`이다. [Tool별 Train 간격 분포](tool_sampling_intervals.csv).

기존 strict 조건은 **실제 60행 이상·관측 첫~마지막 24분 이상·마지막 행 1분 이내**였고 Train **256건(Low 186/High 32/Leak 38)**, Validation **91건(Low 73/High 14/Leak 4)**이다. 이것은 행 수 기준만 느슨한 규칙이어서, 일부 strict 창은 실제 30분 대비 관측률이 낮고 긴 내부 공백이 있다. 새 조건은 strict의 단순 상위 집합이 아니다. 따라서 아래의 **새로 포함된 사건**과 **기존 strict에서 빠진 사건**을 나눠 기록했다.

## 관측률·시간 폭·최근성 조건

관측률 **50/67/80/90%**, 관측 시간 폭 **15/20/24분**, 마지막 관측 최근성 **1/3/5분/제한 없음**의 모든 조합을 [조건별 사건 수와 strict 교집합](threshold_event_counts.csv)에 저장했다. 비교를 위해 시간 폭 **20분**, 최근성 **3분**을 같게 놓으면:

| 관측률 | Train | Validation | strict 대비 순증 Train / Validation |
|---|---:|---:|---:|
| ≥50% | 270 | 93 | +14 / +2 |
| ≥67% | 263 | 90 | +7 / −1 |
| ≥80% | 240 | 77 | −16 / −14 |
| ≥90% | 182 | 56 | −74 / −35 |

이번 감사에서 어떤 수치를 성능 최적 기준으로 선택한 것은 아니다. 특히 관측률을 높이면 이력 품질은 엄격해지지만 고유 고장 사건과 Tool coverage가 줄어든다.

## 요청한 Candidate A/B/C

| 조건 | Train Low / High / Leak = 전체 | Validation Low / High / Leak = 전체 | 전체 사건 | strict 대비 새로 포함 / 빠짐 | Tool 수 |
|---|---:|---:|---:|---:|---:|
| 기존 strict | 186 / 32 / 38 = **256** | 73 / 14 / 4 = **91** | **347** | 기준 | 20 |
| **A:** 50%·15분·5분 | 205 / 36 / 40 = **281** | 75 / 15 / 5 = **95** | **376** | **39 / 10**, 순증 +29 | 19 |
| **B:** 67%·20분·3분 | 190 / 33 / 40 = **263** | 70 / 15 / 5 = **90** | **353** | **24 / 18**, 순증 +6 | 19 |
| **C:** 80%·24분·1분 | 165 / 28 / 35 = **228** | 58 / 12 / 3 = **73** | **301** | **0 / 46**, 순감 −46 | 17 |

후보 A는 Train에서 새 **32건**을 넣고 기존 **7건**을 빼서 순증 **25건(+9.8%)**, Validation에서는 새 **7건**을 넣고 기존 **3건**을 빼서 순증 **4건(+4.4%)**이다. 50%를 적용할 때 사라지는 strict 10건은 모두 관측률 50% 미만이며 최대 내부 gap 중앙값이 **1,150초**였다. 이들과 달리 A가 추가한 39건의 최대 gap 중앙값은 **84초**, 마지막 관측 지연 중앙값은 **76초**다. 즉 A는 일부 저밀도·긴 공백 사건을 교체한다. 하지만 최대 허용 지연 5분이 실제 유형 판단에 충분한지는 이번 무학습 감사로 알 수 없다. [후보별 유형·분할·증감](candidate_comparison.csv).

Validation Leak는 strict **4건 → A/B 5건**, C **3건**이다. 한 사건 증가로는 Leak 일반화 성능을 안정적으로 검증할 수 없다. High도 Validation **14→15건** 증가에 그친다.

## Feature와 Tool 편중

실제 관측값만으로 기존 Model 2의 9센서 × 8통계 **72개 feature**, 그리고 p25/p75까지 포함한 **90개 후보 통계**를 계산 가능 여부만 확인했다. strict와 A/B/C의 Train·Validation 모두 **feature NaN 0건, slope 수치 계산 불가 0건**이다. 다만 slope가 계산된다는 것이 신뢰할 만한 시간 추세라는 뜻은 아니다. 최대 내부 gap 10분 초과 또는 관측의 90% 초과가 창 한쪽 절반에 몰린 경우는 strict **17건**, A **8건**, B/C **0건**이었다. 이 10분·90%는 기술적 민감도 표식이며 학습 성능으로 고른 기준이 아니다. [후보별 결측·slope 품질](feature_nan_rates.csv).

전체 347 strict 사건에서 `03_M02` **157건(45.2%)**, `06_M02` **33건(9.5%)**, `09_M02` **10건(2.9%)**이다. A의 376건에서는 각각 **167건(44.4%)**, **35건(9.3%)**, **12건(3.2%)**으로, 세 Tool 중 한 대가 새 표본 증가를 독점하지는 않았다. 그러나 `03_M02`의 절대 편중은 여전히 크다. A에서는 strict에 있던 `07_M02` 사건 1건이 빠져 전체 Tool 수가 **20→19대**가 된다. [Tool별 새로 포함·탈락·비중](tool_distribution.csv).

## 누수 검사와 판단

모든 후보의 실제 센서 마지막 시각은 예측 시각 이하이고, 예측 시각은 고장 이전이다. 미래 센서 사용 **0건**, 시간 순서 위반 **0건**, 예약·제외 사건 사용 **0건**, Train/Validation 사건 중복 **0건**이다. [자동 검사](leakage_check.csv).

**기존 strict가 사건을 일부 버리기는 했지만, 이번 완화로 확보한 증가는 제한적이다.** 관측률 50% 후보 A가 데이터 가용성 측면에서는 세 후보 중 가장 넓고 결측 feature도 없으나, Validation은 4건만 순증하고 Leak는 4→5건에 그친다. B는 더 최근·촘촘한 이력을 요구하지만 Validation 총수가 줄고, C는 순수하게 더 엄격해진다. 따라서 A는 *후속 단일 대조 실험의 후보*로 기록할 수 있으나, 이번 사건 수 증가만으로 Random Forest Model 2를 다시 학습하면 성능이 의미 있게 개선된다고 판단할 근거는 부족하다. 특히 이전 실제 Model 1 관리자 알림 평가에서의 High/Leak 구분 실패는 고장 30분 전 표본과 실제 알림 시점의 차이가 핵심이므로, 품질 기준만 완화해 해결된다고 기대하면 안 된다.
