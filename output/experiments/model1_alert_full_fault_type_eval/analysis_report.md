# Model 1 관리자 알림 시점의 저장된 Model 2 고장 유형 평가

새 모델 학습, 기존 설정·시간 분할·모델 파일 변경은 없었다. Model 1 개별 관리자 알림 시각은 이전 결과에 파일로 저장되어 있지 않아, **해시가 일치하는 저장 Validation score**에 기존 규칙인 **threshold 0.34 → 같은 Tool의 threshold hit가 10분 초과 끊기면 새 raw alarm → 마지막 발송 알림에서 30분 cooldown**을 같은 함수로 적용하여 결정적으로 재구성했다. fold 사이 24시간을 제거하는 기존 cooldown *안정성 감사*와 달리 이 평가는 전체 기존 Validation 시간축의 관리자 알림을 대상으로 한다. Model 1과 Random Forest Model 2는 로드만 했다. [고정 설정과 파일 해시](config.json), [모든 관리자 알림 시각](manager_alert_population.csv).

## 대상과 입력 검증

저장된 score에서 raw alarm **7,317건**, cooldown으로 억제한 반복 알림 **863건**, 실제 관리자 알림 **6,454건**을 얻었다. 각 알림 시각 `t` 직전의 실제 30분 센서 관측만 사용해, Model 2 학습 때와 같은 9개 센서 × 8개 통계량 **72개 feature**를 다시 계산했다. 이전에 발생한 고장과 Validation 시작 시각은 센서 이력의 과거 경계로만 사용했다. *다음* 고장시각·TTF·유형·Tool ID는 모델 입력에 사용하지 않았다. 필요한 30분 실제 센서가 없어 모델에 넣지 못한 경우를 따로 남겼다. [알림별 품질·분류](manager_alert_population.csv), [실제 입력 feature](model2_features_at_alerts.csv).

| 분류 | 관리자 알림 수 | 의미 |
|---|---:|---|
| A | **2,664** | 30분 이력 충분, 다음 실제 고장이 Validation 종료 전에 확인됨. 유형 성능 평가 대상 |
| B | **2,697** | 다음 고장은 확인됐지만 30분 이력 부족 |
| C | **1,093** | Validation 종료 전 다음 고장 확인 불가, 정답 유형 미확정 |

C 중 **577건은 이력도 부족**하다. A/B/C는 서로 배타적으로 만들기 위해 다음 고장 확인 여부를 먼저 적용했고, 두 결손 여부는 별도 열로 모두 저장했다. A의 2,664개 알림은 다음 고장 **139개 사건**에 대응하며, 사건 유형은 Low **108**, High **28**, Leak **3**이다. 단일 사건에서 여러 알림을 받으므로 alert-level 수치만으로 결론내리지 않았다. 자동 확인에서 `last_sensor_timestamp > alert_timestamp` **0건**, TTF·고장유형·Tool ID feature **0개**다.

## 알림 및 사건 단위 성능

| 평가 | 사건/알림 수 | Macro F1 | Balanced Accuracy | Low Recall | High Recall | Leak Recall |
|---|---:|---:|---:|---:|---:|---:|
| **실제 관리자 알림** | 2,664 알림 | **0.305** | **0.324** | 0.849 | 0.085 | 0.040 |
| 사건별 **첫** 알림 | 139 사건 | 0.333 | 0.400 | 0.759 | 0.107 | 0.333 |
| 사건별 **마지막** 알림 | 139 사건 | 0.325 | 0.313 | 0.833 | 0.107 | 0 |
| 사건별 알림 score **평균** | 139 사건 | 0.330 | 0.335 | 0.898 | 0.107 | 0 |
| 고장 30분 전 조건부 baseline | 91 사건 | 0.603 | 0.611 | 0.904 | 0.429 | 0.500 |

고장 30분 전 baseline과 이 평가의 **시점·표본·사건 가중이 다르므로**, 수치 차이를 순수한 모델 성능 하락량으로 해석하면 안 된다. 그러나 실제 관리자 알림에서 High·Leak 구분이 거의 되지 않는다는 운영상 결론은 분명하다. 알림 단위 Accuracy는 **56.9%**이며 High 알림 **709건 중 60건**, Leak 알림 **253건 중 10건**만 맞혔다. 가장 큰 오진은 **실제 High → Low 531알림**, **실제 Leak → Low 235알림**이다. [알림 지표](alert_level_metrics.csv), [유형별 P/R/F1](alert_class_metrics.csv), [혼동 행렬](alert_confusion_matrix.csv), [사건 첫·마지막·평균 score 비교](event_level_metrics.csv).

같은 2,664개 평가 알림에서 항상 Low를 표시하는 단순 기준의 Macro F1은 **0.260**, Balanced Accuracy는 **0.333**이다. 저장 Model 2의 Macro F1 **0.305**는 이보다 조금 높지만 Balanced Accuracy **0.324**는 오히려 낮다.

각 구간의 유형 구성이 다르고 일부에는 Leak가 없으므로 구간별 수치를 직접 순위화하면 안 된다. 평가 가능한 알림의 **75%가량(1,992/2,664)**은 다음 고장까지 72시간 이상이다. 고장 30분 전만으로 학습한 Model 2가 이 먼 시점들까지 일반화된다는 근거는 없다. [전체 구간별 유형 support와 Recall](lead_time_metrics.csv).

Random Forest의 최대 class score는 **보정된 확률이 아니다**. 사전에 지정된 네 기준을 그대로 평가했다.

| 최대 score ≥ | 유형 표시 알림 | coverage | 표시된 알림 정답률 | 오진 | Low/High/Leak 표시 |
|---|---:|---:|---:|---:|---:|
| 0.5 | 2,237 | 84.0% | 60.9% | 875 | 1,988 / 68 / 181 |
| 0.6 | 1,525 | 57.2% | 69.3% | 468 | 1,486 / 21 / 18 |
| 0.7 | 973 | 36.5% | 79.8% | 197 | 971 / 1 / 1 |
| 0.8 | 356 | 13.4% | 86.5% | 48 | 355 / 0 / 1 |

고장 30분 전 baseline의 score ≥0.7은 **coverage 59.3% / 표시 정답률 94.4%**였으나 실제 알림에서는 **36.5% / 79.8%**다. 0.7에서 High/Leak는 각각 **1건만 표시**되어 거의 Low 전용 표시가 된다. 이것을 High·Leak 유형 예측의 안전한 필터로 해석할 수 없다. [기준별 사건 수·유형별 정답 수](confidence_thresholds.csv).

## 반복 알림과 대시보드 판단

평가 가능한 **139개 사건 중 109개**에서 관리자 알림이 2회 이상 있었다. 같은 사건의 인접 알림 **2,525쌍 중 1,985쌍(78.6%)**은 유형이 같고, **540회** 유형이 바뀌었다. 반복 사건에서 마지막 알림이 맞은 비율은 **68.8%**이나, 마지막 알림 사건 단위 High Recall은 **10.7%**, Leak Recall은 **0/3**이다. 마지막 시점으로 바꿔도 유형 신뢰성이 회복되지 않는다. [사건별 알림 순서·변경 횟수](repeated_alert_stability.csv), [사건별 세 가지 대표 예측](event_predictions.csv).

**지금 Model 2를 대시보드의 다음 고장 유형 표시로 연결할 근거는 없다.** 확정적인 `다음 고장 유형: Low Pressure`는 물론 `참고 고장 유형`도 High/Leak 오진이 너무 많다. `score < 0.7` 판단 보류를 추가해도 표시된 거의 모든 결과가 Low가 되고 오진 197건이 남는다. 0.7은 이미 정해진 평가 기준으로만 사용했으며 운영 threshold로 채택하지 않았다. 이 모델은 고장 30분 전 조건부 연구 baseline으로 유지하고, 실제 Model 1 알림 시점의 유형 정보를 제공하려면 **알림 시점과 시간순 사건 단위로 새로 설계한 학습·독립 검증**이 필요하다.
